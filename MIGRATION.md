## 1. Схемы размещения

| Схема | Плюсы | Минусы |
|-------|-------|--------|
| **Один сервер** | Простота, `127.0.0.1` между ботом и панелью, нет туннеля | Ресурсы делятся (712 МБ RAM на панель+бот — впритык) |
| **Бот в РФ, панель за границей** | Ресурсы раздельны, панель изолирована | Нужен SSH-туннель для Telegram |
| **Бот за границей, панель там же** | Telegram доступен, `127.0.0.1` | Нужен VPN для клиентов внутри РФ |

**Если у тебя Alpine 84.252.73.114 (РФ) и панель на Debian 185.200.190.40 — это схема 2.**

## 2. Бот и панель на одном сервере

Трафик между ботом и панелью не покидает машину — MITM физически невозможен.

### Что делать

1. **Проверь, что панель слушает на `0.0.0.0` или `127.0.0.1`.**
   В 3x-ui: **Настройки панели → Panel Listen IP**.

2. **В `config.yml` укажи локальный URL:**

   ```yaml
   panels:
     "TMT":
       url: "https://127.0.0.1:24487/PATH"
       username: "admin"
       password: "..."
       sub_url: "https://PUBLIC_IP:2096/sub"
   ```

3. **Запусти бота.** В логе:
   ```
   Локальный адрес — SSL-проверка отключена (безопасно).
   ```

**Сертификат не нужен.** `verify=False` для `127.0.0.1` безопасен.

**Если Telegram блокируется** — всё равно нужен SSH SOCKS5-туннель (раздел 3).

## 3. Бот в РФ, панель за границей (SSH-туннель)

Наш случай. Alpine в РФ с ботом, Debian за границей с панелью.

### 3.1. Проверка блокировки

С Alpine:

```bash
curl -s --max-time 10 https://api.telegram.org/bot123:test/getMe
```

- **JSON** `{"ok":false,...}` — Telegram доступен, туннель не нужен.
- **Timeout** — блокируется, туннель обязателен.

### 3.2. SSH-ключ

```bash
ssh-keygen -t ed25519 -C "tunnel@xuihelper" -f ~/.ssh/id_ed25519 -N ""
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@YOUR_REMOTE_SERVER
ssh -o PasswordAuthentication=no root@YOUR_REMOTE_SERVER "echo OK"
```

**Что ожидать:** `OK` без пароля.

### 3.3. SOCKS5-туннель как сервис

См. раздел 10.6 в `MANUAL.md` — там полный конфиг `/etc/init.d/tg-tunnel`.

### 3.4. Проверка

```bash
ss -tlnp | grep 1080
curl -s --max-time 10 --proxy socks5h://127.0.0.1:1080 https://api.telegram.org/bot123:test/getMe
```

**Обязательно `socks5h://`** — тогда DNS-резолв произойдёт на удалённом сервере. Иначе может выйти так: curl резолвит Telegram, получает IPv6-адрес, а удалённый сервер не имеет IPv6-маршрута → соединение рвётся.

### 3.5. Запуск бота с прокси

Прокси передаются через переменные окружения:

```bash
export HTTPS_PROXY=socks5://127.0.0.1:1080
export HTTP_PROXY=socks5://127.0.0.1:1080
export ALL_PROXY=socks5://127.0.0.1:1080

python3 main.py
```

**`httpx` и `python-telegram-bot` читают эти переменные автоматически** — код менять не нужно.

## 4. SSL между ботом и панелью

`xui_api.py` содержит функцию `_resolve_verify_setting`, которая:

- Для `127.0.0.1` / `localhost` → `verify=False` (безопасно, трафик не покидает машину).
- Для внешнего адреса → `SSLContext` с полной проверкой цепочки через системные корни, но `check_hostname=False`. Это нужно, потому что панель доступна по IP, а сертификат может быть выписан на домен.

### 4.1. С Let's Encrypt (рекомендуется)

Ничего не делаешь. Сертификат Let's Encrypt доверенный, `httpx` проверяет цепочку автоматически.

В логе:

```
Внешний адрес — проверка цепочки через системные корни.
```

### 4.2. С самоподписанным сертификатом

Нужно положить CA bundle в проект. Скачай `fullchain.pem` с панели:

```bash
scp root@PANEL_HOST:/root/cert/ip/fullchain.pem ./certs/panel_cert.pem
```

И расширь `_resolve_verify_setting` в `xui_api.py`, чтобы он использовал `certs/panel_cert.pem` как CA bundle для внешних адресов.

### 4.3. Проверка SSL

1. Открой `config.yml`.
2. Если URL панели начинается с `https://127.0.0.1` — MITM невозможен.
3. Если URL внешний — в логе должна быть строка про проверку цепочки.
4. Если в логе предупреждение «нет CA bundle — verify=True без сертификата упадёт» — конфигурация опасная, правь.

## 5. Переезд бота между серверами

### 5.1. Подготовка на старом сервере

```bash
rc-service xuihelper stop
rc-service tg-tunnel stop

tar czf xuihelper-backup.tar.gz \
    /root/XUIHelper/config.yml \
    /root/XUIHelper/data/
```

**Что НЕ нужно переносить:**
- Код (`.py`) — берём из git.
- `.venv/` — создаём заново.
- Логи.

**Что нужно перенести:**
- `config.yml` (секреты).
- `data/traffic.db` (история, привязки клиентов).

### 5.2. На новом сервере

```bash
# 1. Установить зависимости
apk add --no-cache git python3 py3-pip gcc make musl-dev \
    python3-dev libffi-dev openssl-dev yaml-dev tzdata logrotate

# 2. Клонировать проект
cd /root
git clone https://github.com/iskanderinka/XUIHelper.git
cd XUIHelper

# 3. Восстановить данные
tar xzf /tmp/xuihelper-backup.tar.gz --strip-components=2 -C /root/XUIHelper

# 4. Окружение
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 5. Настроить туннель (если нужен)
#    См. раздел 3 этой инструкции.

# 6. Настроить OpenRC-сервис
#    См. раздел 10.7 в MANUAL.md.
```

### 5.3. Проверка

```bash
rc-service xuihelper status
tail -20 /var/log/xuihelper.err
```

В Telegram: `/status TMT` — должен ответить.

## 6. Часовой пояс

```yaml
timezone: "Asia/Hong_Kong"
```

Полный список: https://en.wikipedia.org/wiki/List_of_tz_database_time_zones

**При опечатке** — бот откатывается на `Asia/Hong_Kong`.

**После смены нужен перезапуск бота:**

```bash
rc-service xuihelper restart
```

Уже сохранённые даты клиентов не меняются — только новые операции будут считаться в новой зоне.

**На Alpine** убедись, что установлен `tzdata`:

```bash
apk add --no-cache tzdata
```
