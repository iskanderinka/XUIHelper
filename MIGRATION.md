## Сценарий 1. Бот и панель на одном сервере (рекомендуемый для прода)

Трафик между ботом и панелью не покидает машину — MITM физически невозможен.

### Что делать

1. **Проверь, что панель слушает на `0.0.0.0` или `127.0.0.1`.**
   В 3x-ui: **Настройки панели → Panel Listen IP**.

2. **В `config.yml` укажи URL панели через локальный адрес:**

   ```yaml
   panels:
     "TMT":
       url: "https://127.0.0.1:24487/x8UGpUW143YI9P3JVyQm"
       username: "mvernita"
       password: "..."
       sub_url: "https://185.200.190.40:2096/sub"
   ```

   **`sub_url` оставь внешним.** Клиенты ходят снаружи.

3. **Запусти бота.** В логе увидишь:
   ```
   Локальный адрес — SSL-проверка отключена (безопасно).
   ```

**Никаких сертификатов не нужно.** `verify=False` для `127.0.0.1` безопасен.

## Сценарий 2. Бот на ноуте, панель на удалённом сервере (разработка)

### Что делать

1. **В `config.yml` укажи внешний URL панели:**

   ```yaml
   panels:
     "TMT":
       url: "https://185.200.190.40:24487/x8UGpUW143YI9P3JVyQm"
       username: "mvernita"
       password: "..."
       sub_url: "https://185.200.190.40:2096/sub"
   ```

2. **Сертификат Let's Encrypt работает автоматически.** Ничего скачивать не надо.
   В логе:
   ```
   Внешний адрес — проверка цепочки через системные корни.
   ```

### Если сертификат самоподписанный

Скачай `fullchain.pem` с сервера панели:

```bash
scp root@panel_ip:/root/cert/ip/fullchain.pem ./certs/panel_cert.pem
```

Создай папку `certs/`, если её нет:

```bash
mkdir -p certs
```

Для самоподписанных сертификатов потребуется расширить `_resolve_verify_setting`
в `xui_api.py`, чтобы он использовал `certs/panel_cert.pem` как CA bundle.

## Сценарий 3. Переезд бота между серверами

### Шаг 1. Подготовка на старом сервере

1. Останови бота:
   ```bash
   systemctl stop xuihelper    # для systemd
   # или docker-compose down   # для Docker
   ```

2. Сделай резервную копию:
   ```bash
   tar czf xuihelper-backup.tar.gz \
       config.yml \
       data/ \
       *.py \
       requirements.txt
   ```

### Шаг 2. Перенос

1. Скачай архив на новый сервер:
   ```bash
   scp xuihelper-backup.tar.gz root@new_server:/root/
   ```

2. Распакуй:
   ```bash
   ssh root@new_server
   mkdir -p /root/XUIHelper
   cd /root/XUIHelper
   tar xzf /root/xuihelper-backup.tar.gz
   ```

### Шаг 3. Настройка на новом сервере

1. **Проверь `config.yml`** — если бот и панель теперь на одном сервере,
   поменяй URL панели на `127.0.0.1`.

2. **Восстанови окружение:**

   ```bash
   pyenv local 3.11.9
   python -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

3. **Настрой systemd-сервис** (см. `MANUAL.md`, раздел 10).

4. **Запусти:**
   ```bash
   systemctl start xuihelper
   systemctl status xuihelper
   ```

5. **Проверь в Telegram:** `/status TMT` — должен ответить статусом панели.

### Шаг 4. Старый сервер

После успешного переезда останови бота на старом сервере и удали.

## Часовой пояс

Планировщик и расчёт «конца дня» работают в часовом поясе из `config.yml`:

```yaml
timezone: "Asia/Hong_Kong"
```

Полный список зон: https://en.wikipedia.org/wiki/List_of_tz_database_time_zones

При опечатке бот использует `Asia/Hong_Kong` как fallback.

**После смены `timezone` нужен перезапуск бота.** Уже сохранённые даты клиентов
не меняются — только новые операции будут считаться в новой зоне.

## Проверка SSL

Чтобы убедиться, что всё работает правильно:

1. Открой `config.yml`.
2. Если URL панели начинается с `https://127.0.0.1` или `https://localhost` —
   всё в порядке, MITM невозможен.
3. Если URL внешний — проверь, что в логе есть строка
   «Внешний адрес — проверка цепочки через системные корни».
4. Если в логе предупреждение «нет CA bundle — verify=True без сертификата
   упадёт» — ты в опасной конфигурации, надо её поправить.
