## 1. Схемы размещения

| Схема | Плюсы | Минусы |
|-------|-------|--------|
| **Один сервер** | Простота, `127.0.0.1` между ботом и панелью, нет туннеля | Ресурсы делятся (~700 МБ RAM на панель+бот — впритык) |
| **Бот в РФ, панель за границей** | Ресурсы раздельны, панель изолирована | Нужен SSH-туннель для Telegram |
| **Бот и панель за границей** | Telegram доступен напрямую, `127.0.0.1` | Клиентам в РФ/ТМ нужен рабочий протокол |

**Типовые сценарии:**

- Alpine в РФ + Debian за границей → **схема 2** (туннель).
- Один сервер в Амстердаме → **схема 3** (без туннеля, но бот должен уметь ходить в Telegram).

## 2. Бот и панель на одном сервере

Трафик между ботом и панелью не покидает машину — MITM физически невозможен.

### Что делать

1. **Проверь, что панель слушает на `0.0.0.0` или `127.0.0.1`.**
   В 3x-ui: **Настройки панели → Panel Listen IP**.

2. **В `config.yml` укажи локальный URL:**

   ```yaml
   panels:
     "PANEL_NAME":
       url: "https://127.0.0.1:<PANEL_PORT>/<WEB_BASE_PATH>"
       username: "<panel_login>"
       password: "<panel_password>"
       sub_url: "https://<PUBLIC_IP>:<SUB_PORT>/<SUB_PATH>"
   ```

3. **Запусти бота.** В логе:
   ```
   Локальный адрес — SSL-проверка отключена (безопасно).
   ```

**Сертификат панели при этом не нужен** — `verify=False` для `127.0.0.1` безопасен.

**Если Telegram блокируется** — всё равно нужен SSH SOCKS5-туннель (раздел 3).

## 3. Бот отдельно, панель за границей (SSH-туннель)

Типовой случай: бот на РФ-сервере (Alpine), панель на зарубежном (Debian).

### 3.1. Проверка блокировки

С РФ-сервера:

```bash
curl -s --max-time 10 https://api.telegram.org/bot123:test/getMe
```

- **JSON** `{"ok":false,...}` — Telegram доступен, туннель не нужен.
- **Timeout** — блокируется, туннель обязателен.

### 3.2. SSH-ключ

```bash
ssh-keygen -t ed25519 -C "tunnel@xuihelper" -f ~/.ssh/id_ed25519 -N ""
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<REMOTE_SERVER>
ssh -o PasswordAuthentication=no root@<REMOTE_SERVER> "echo OK"
```

**Что ожидать:** `OK` без пароля.

### 3.3. SOCKS5-туннель как сервис

Полный конфиг `/etc/init.d/tg-tunnel` — в `MANUAL.md`, раздел 11.6.

Ключевые параметры:

```bash
command_args="-N -D 127.0.0.1:1080 \
    -o ServerAliveInterval=30 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -o StrictHostKeyChecking=accept-new \
    -o BatchMode=yes \
    root@<REMOTE_SERVER>"
```

`ServerAliveInterval=30` и `ServerAliveCountMax=3` — SSH сам отваливается через 90 секунд молчания. Это правильно: если сервер недоступен, лучше отвалиться и не висеть.

### 3.4. Проверка

```bash
ss -tlnp | grep 1080
curl -s --max-time 10 --proxy socks5h://127.0.0.1:1080 https://api.telegram.org/bot123:test/getMe
```

**Обязательно `socks5h://`** — тогда DNS-резолв произойдёт на удалённом сервере. Иначе получится так: curl резолвит Telegram у себя, получает IPv6-адрес, а у удалённого сервера может не быть IPv6-маршрута → соединение рвётся.

### 3.5. Запуск бота с прокси

Прокси передаются через переменные окружения в `/etc/init.d/xuihelper`:

```bash
export HTTPS_PROXY="socks5://127.0.0.1:1080"
export HTTP_PROXY="socks5://127.0.0.1:1080"
export ALL_PROXY="socks5://127.0.0.1:1080"
export NO_PROXY="127.0.0.1,localhost"
```

**`httpx` и `python-telegram-bot` читают эти переменные автоматически** — код менять не нужно.

**Про `NO_PROXY`:** без него `httpx` погонит через SOCKS5 и запросы к панели (лишний крюк, панель увидит их с IP туннеля). Если панель имеет внешний IP — добавь его в список.

### 3.6. Что делать, если туннель падает

SSH-туннель — штука хрупкая. Может упасть при:
- Ребут удалённого сервера.
- Сетевых провалах между РФ и зарубежкой.
- Проблемах с DNS.

**Симптом падения:**
- `rc-service tg-tunnel status` → `crashed`
- `ss -tlnp | grep 1080` → пусто
- В `xuihelper.err` — `NetworkError: httpx.ConnectError`

**Быстрый рецепт восстановления:**

```bash
# 1. Рестарт туннеля
rc-service tg-tunnel restart
sleep 3
ss -tlnp | grep 1080

# 2. Проверка, что туннель работает
curl -s --max-time 10 --proxy socks5h://127.0.0.1:1080 https://api.telegram.org/bot123:test/getMe

# 3. Рестарт бота
rc-service xuihelper restart
```

**Автоматизация (cron-сторож):**

Раз в 5 минут проверять, слушает ли 1080, и если нет — поднимать:

```bash
mkdir -p /etc/periodic/5min
cat > /etc/periodic/5min/check-tunnel << 'EOF'
#!/bin/sh
if ! ss -tln | grep -q ':1080 '; then
    logger -t check-tunnel "Порт 1080 пуст, поднимаю tg-tunnel"
    rc-service tg-tunnel restart
fi
EOF
chmod +x /etc/periodic/5min/check-tunnel
rc-service crond restart
```

## 4. SSL для панели

Панель 3x-ui должна отдавать HTTPS. Возможные способы.

### 4.1. Let's Encrypt for IP (рекомендуется)

Самый простой вариант, **не требует домена**. Поддерживается в 3.8.5 из коробки.

**Как выпускается:**

При установке панели (скрипт `install.sh`) предлагается выбор SSL. Нужно выбрать **опцию 2 — «Let's Encrypt for IP Address»**. Установщик:

1. Создаст сертификат на публичный IP через **TLS-ALPN-01**.
2. Установит `acme.sh` в `~/.acme.sh/`.
3. Настроит cron на автопродление **4 раза в день** (в 00:30, 06:30, 12:30, 18:30).
4. Положит файлы в `/root/cert/ip/fullchain.pem` и `/root/cert/ip/privkey.pem`.

**Срок сертификата — 6–7 дней.** Это нормально, потому что продление автоматическое.

**Порт 80 не нужен** — LE for IP валидируется через порт 443 (TLS-ALPN-01).

**Проверка состояния:**

```bash
# Что за сертификат
openssl x509 -in /root/cert/ip/fullchain.pem -noout -dates

# Должно быть notAfter в будущем на 5–7 дней

# Что за cron
crontab -l | grep acme

# Ожидаем:
# 30 0,6,12,18 * * * "/root/.acme.sh"/acme.sh --cron --home "/root/.acme.sh" > /dev/null

# Директория acme.sh
ls ~/.acme.sh/
# Должна быть папка вида <PANEL_IP>_ecc
```

**Когда это не сработает:**

- Если провайдер блокирует **входящий** порт 443 → LE не сможет провалидировать.
- Если DNS на сервере не резолвит `acme-v02.api.letsencrypt.org` → acme.sh не сможет зарегистрироваться.

**Ручное продление, если автопродление сломалось:**

```bash
# Форсировать продление вручную
~/.acme.sh/acme.sh --renew -d <PANEL_IP> --force --ecc

# Перезапустить панель, чтобы она перечитала файлы
x-ui restart
```

### 4.2. Let's Encrypt for Domain (классика)

Если есть домен, направленный на IP панели. Срок — 90 дней, автопродление через acme.sh.

Установка:

```bash
x-ui cert
# В меню выбрать "1. Get SSL (Domain)"
# Ввести домен, выбрать валидацию (HTTP-01 или DNS-01)
```

**Минусы:** нужен домен + DNS. **Плюсы:** срок 90 дней вместо 7.

### 4.3. ZeroSSL (альтернатива LE)

Аналог LE, но другой CA. Работает через тот же ACME. Иногда проходит там, где LE заблокирован.

**Для IP** — только ручной выпуск через веб-интерфейс ZeroSSL, **без автопродления**. Срок 90 дней, раз в 3 месяца заходить и перевыпускать. **Не рекомендуется**, если работает LE for IP.

**Для домена** — через `acme.sh` с указанием ZeroSSL как CA:

```bash
~/.acme.sh/acme.sh --register-account --server zerossl
~/.acme.sh/acme.sh --issue -d <your_domain> --server zerossl
```

### 4.4. Самоподписанный сертификат

Если ничего не работает.

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
    -keyout /root/cert/ip/privkey.pem \
    -out /root/cert/ip/fullchain.pem \
    -days 365 -subj "/CN=<PANEL_IP>"
```

**Минусы:** браузеры и клиенты показывают предупреждение. Для бота не критично (бот использует `verify=False` для панели), но для клиентов, заходящих в sub-ссылку из браузера — неудобно.

## 5. SSL между ботом и панелью

`xui_api.py` содержит функцию `_resolve_verify_setting`, которая определяет, как бот проверяет сертификат панели.

### 5.1. Как это работает

- **Для `127.0.0.1` / `localhost` / `::1`** → `verify=False`. Безопасно, потому что трафик не покидает машину.
- **Для внешнего адреса** → `SSLContext` с **полной проверкой цепочки** через системные корни, но **`check_hostname=False`**. Это нужно, потому что панель доступна по IP, а сертификат может быть выписан на домен или на IP.

**В логе:**

```
Локальный адрес — SSL-проверка отключена (безопасно).
```
или
```
Внешний адрес — проверка цепочки через системные корни.
```

### 5.2. Что делать при смене сертификата панели

Если админ перевыпустил сертификат на панели (например, acme.sh автоматически), бот **ничего не должен делать** — при следующем запросе `httpx` получит новый сертификат и проверит его по тем же правилам.

**Что может сломаться:** если сертификат стал самоподписанным или истёк — `httpx` вернёт `SSLCertVerificationError`. В логе будет трейсбек. Лечится: `rc-service xuihelper restart` (иногда httpx кэширует SSL-контекст).

### 5.3. Если сертификат самоподписанный

Для внешнего адреса бот не доверяет самоподписанному сертификату. Есть два пути:

**Путь 1 — не использовать самоподписанный.** Настрой LE for IP на панели.

**Путь 2 — положить CA в проект.** Скачай `fullchain.pem` с панели, положи в `certs/panel_cert.pem` в проекте, и расширь `_resolve_verify_setting` в `xui_api.py`, чтобы для внешних адресов использовался этот CA bundle.

## 6. Переезд бота между серверами

### 6.1. Что переносим

**Не переносим:**
- Код (`.py`) — берём из git.
- `.venv/` — создаём заново.
- Логи из `/var/log/`.
- `__pycache__/`.

**Переносим:**
- `config.yml` — **секреты**.
- `data/traffic.db` — **вся история**: клиенты, трафик, уведомления.
- `data/audit.log` — **журнал действий админов**.
- `~/.ssh/id_ed25519` — **ключ для туннеля** (если туннель тоже переносится).

### 6.2. Подготовка на старом сервере

**Важно:** `traffic.db` в режиме WAL. Простое копирование может поймать файл в неконсистентном состоянии. Делаем дамп:

```bash
rc-service xuihelper stop
rc-service tg-tunnel stop

# Дамп БД (безопасно, даже если бот ещё пишет)
sqlite3 <PROJECT_DIR>/XUIHelper/data/traffic.db ".backup /tmp/traffic.db.bak"

# Собираем архив
cd <PROJECT_DIR>/XUIHelper
tar czf /tmp/xuihelper-backup.tar.gz \
    config.yml \
    data/audit.log \
    -C /tmp traffic.db.bak
```

### 6.3. На новом сервере

```bash
# 1. Зависимости
apk add --no-cache git python3 py3-pip gcc make musl-dev \
    python3-dev libffi-dev openssl-dev yaml-dev tzdata logrotate

# 2. Клонировать
cd <PROJECT_DIR>
git clone https://github.com/<your-repo>/XUIHelper.git
cd XUIHelper

# 3. Восстановить данные
mkdir -p data
cp /tmp/xuihelper-backup.tar.gz /tmp/
tar xzf /tmp/xuihelper-backup.tar.gz -C /tmp/restore-tmp/
cp /tmp/restore-tmp/config.yml ./
cp /tmp/restore-tmp/traffic.db.bak data/traffic.db
cp /tmp/restore-tmp/data/audit.log data/audit.log 2>/dev/null || true

# 4. Окружение
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 5. Настроить туннель (если нужен) — см. раздел 3.
# 6. Настроить OpenRC-сервисы — см. MANUAL.md, раздел 11.7.
```

### 6.4. Первая проверка

```bash
rc-service xuihelper status
tail -20 /var/log/xuihelper.err
```

В Telegram: `/status <panel>` — должен ответить.

### 6.5. Обязательный `/sync` после переезда

**Сразу после первого запуска выполни `/sync`.** Особенно если:

- Ты восстанавливал `data/traffic.db` из бэкапа.
- В панели что-то менялось вручную после последнего снимка БД.

```
/sync
```

В логе увидишь:

```
✅ <panel>: обновлено N, переименовано M, потеряно K
```

**«Потеряно K»** — связки в БД, которых нет в панели по UUID. Проверь их руками: если клиент действительно удалён — `/revoke`, если переименован — посмотри в панели.

## 7. Часовой пояс

```yaml
timezone: "Asia/Hong_Kong"
```

Полный список: https://en.wikipedia.org/wiki/List_of_tz_database_time_zones

**При опечатке** — бот откатывается на `Asia/Hong_Kong`.

**Что зависит от TZ:**

- Время снимка трафика (`record_traffic_job`).
- Время дневного отчёта.
- Время напоминаний клиентам.
- Расчёт «конца дня» при выдаче подписок.
- **Даты в `audit.log`**.

**После смены нужен перезапуск бота:**

```bash
rc-service xuihelper restart
```

Уже сохранённые даты клиентов не меняются — только новые операции будут считаться в новой зоне.

**На Alpine** убедись, что установлен `tzdata`:

```bash
apk add --no-cache tzdata
```

## 8. Туркменистан

Регион с агрессивной фильтрацией. Ниже — сводка, что важно для развёртывания.

### 8.1. Порт 80 в исходящие — закрыт

**Тест из ТМ:**

```bash
curl -I --connect-timeout 5 --max-time 8 http://www.google.com:80/
```

Если таймаут — провайдер блокирует исходящий трафик на порт 80.

**Что это значит:** стандартный HTTP-01 challenge для Let's Encrypt **не сработает**. Используй **LE for IP** (TLS-ALPN-01 на порту 443) или DNS-01 (если есть домен).

### 8.2. Sub-порт панели — блокируется

**Симптом:** клиент получает sub-ссылку, но она «висит». Из РФ тот же URL работает.

**Что делать:**

- Раздавать клиентам **прямые конфиги** через `/getlink` → «🧩 Ссылки на все конфигурации». Они идут на порты Xray (443, 11440, 14839, 33099, 34910, 48800), которые обычно не блокируются.
- Или поднять sub на 443 через SNI-routing (отдельный домен на порту 443) — сложнее, требует домена и nginx.

### 8.3. UDP/QUIC — режется

**Симптом:** Hysteria2 в подписке, но HAPP не подключается.

**Причина:** Hysteria2 работает поверх UDP. Провайдеры ТМ применяют QoS к UDP/QUIC.

**Что делать:**

- Оставить в подписке только VLESS+Reality (TCP).
- Или дать клиенту один рабочий конфиг VLESS через `/getlink`.

### 8.4. HWID-гейт в 3x-ui 3.8.5+

**Симптом:** sub-ссылка возвращает 404, хотя клиент существует.

**Причина:** при `limit_hwid > 0` панель требует заголовок `X-HWID` в sub-запросе.

**Что делать:**

- Снять HWID-лимит (поставить 0).
- Или использовать HAPP 4.6+.
- Или раздавать конфиги через `/getlink`.

### 8.5. iOS и XHTTP

**Симптом:** подписка с несколькими инбаундами, HAPP на iOS не подключается ни к одному.

**Причина:** XHTTP+Reality не работает на iOS. HAPP спотыкается о первый несовместимый инбаунд и не переключается на следующий.

**Что делать:**

- Держать для iOS-клиентов **отдельные подписки** только с VLESS+TCP.
- Или давать им один рабочий конфиг через `/getlink`.

### 8.6. Проверка доступности панели из ТМ

Полезный набор команд для диагностики с клиентской стороны:

```bash
# Проверить, открыт ли TCP-порт (nc, не всегда есть — pkg install netcat-openbsd)
nc -zv -w 5 <PANEL_IP> <PORT>

# Проверить HTTPS-ответ
curl -sk --connect-timeout 5 -o /dev/null -w "HTTP %{http_code}\n" "https://<PANEL_IP>:<PORT>/"

# Проверить размер и время отдачи sub
curl -sk --connect-timeout 5 --max-time 15 \
    -w "\nHTTP %{http_code}, size %{size_download}, time %{time_total}\n" \
    "https://<PANEL_IP>:<SUB_PORT>/<SUB_PATH>/<SUB_ID>"
```

Что смотреть:
- **TCP FAIL / timeout** → порт блокируется.
- **HTTP 404** → порт открыт, но sub не отдаёт (возможно, HWID-гейт или неверный subId).
- **HTTP 200, size > 1000** → всё работает.

## 9. Переезд панели (не бота)

Если меняется IP панели:

1. **Обновить `config.yml`** на РФ-сервере: `url` и `sub_url` панели.
2. **Рестарт бота:**
   ```bash
   rc-service xuihelper restart
   ```
3. **Проверить связь:**
   ```
   /listpanels
   /status <panel>
   ```
4. **`/sync`** — на случай, если с момента переезда в панели что-то менялось.
