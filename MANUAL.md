# Руководство по эксплуатации XUIHelper

## 1. Обзор

XUIHelper — Telegram-бот для управления несколькими панелями 3x-ui: создаёт клиентов, выдаёт ссылки подписки и прямые конфигурации, следит за сроком действия, поддерживает паузу и продление, ведёт статистику трафика, присылает дневные отчёты и ведёт журнал действий админов.

Три роли:

- **Клиент**: получает подписку и кнопки быстрого доступа, отправляет заявки, смотрит свой гайд.
- **Администратор**: создаёт клиентов, управляет подписками, смотрит статистику.
- **Суперадмин** (первый в списке): управляет панелями, синхронизацией, удалением.

## 3. Требования

- Python 3.11+
- Зависимости из `requirements.txt`
- Панель 3x-ui версии **3.8.5** или новее (используется API `/panel/api/clients/links/:email`)

## 5. Первичная настройка

### 5.1. `config.yml`

Скопируй `config.yml.example` в `config.yml` и заполни:

```yaml
bot_token: "YOUR_TELEGRAM_BOT_TOKEN"

timezone: "Asia/Hong_Kong"

users:
  # Список ID администраторов. ПЕРВЫЙ — суперадмин.
  # Без суперадмина админские команды не работают.
  admin_users:
    - <superadmin_tg_id>    # ← суперадмин
    - <admin_tg_id>         # обычный админ (опционально)

panels:
  "PANEL_NAME":
    url: "https://<PANEL_IP>:<PANEL_PORT>/<WEB_BASE_PATH>"
    username: "<panel_login>"
    password: "<panel_password>"
    sub_url: "https://<PANEL_IP>:<SUB_PORT>/<SUB_PATH>"

traffic:
  accounting_mode: unidirectional

policy:
  url: ""
  message: ""

tariffs:
  url: ""
  message: ""

guide:
  client:
    url: ""
    message: ""
  admin:
    url: ""
    message: ""
  superadmin:
    url: ""
    message: ""
```

**Важно:**

- `url` панели — **без завершающего слеша**, содержит кастомный webBasePath (если настроен).
- `sub_url` — тоже **без завершающего слеша**, содержит кастомный sub-path панели.
- Если бот и панель на одном сервере — `url` можно указать с `127.0.0.1`.
- Если панель за границей — `url` указывает на публичный IP (см. `MIGRATION.md`).

python3 -m venv .venv

### 6.7. Изменение данных клиента

**Комментарий** (`/setcomment`):

```
/setcomment <tg_id> <email> Иван, оплатил до конца года
```

Обновляется **и в БД, и в панели**. Чтобы очистить комментарий, используй `-`:

```
/setcomment <tg_id> <email> -
```

**Email** (`/rename`):

```
/rename <tg_id> <old_email> <new_email>
```

Обновляется **в БД, в панели и в истории трафика**. Работает и при смене имени в промо-периоде (например, `prm_*` → `*`).

**Требования:**
- Новый email не должен быть занят ни в БД, ни в панели.
- Только латиница, цифры, точка, дефис, подчёркивание.
- Длина 1–64 символа.

### 6.8. Синхронизация с панелью (`/sync`)

Обычно бот **сам** пишет изменения в БД и в панель одновременно. Но если админ менял что-то **руками** в панели (email, комментарий, HWID, срок) — данные разошлись.

**`/sync`** (только суперадмин):

- Обходит все панели.
- Находит связки **по UUID**.
- Обновляет в БД: email, комментарий, HWID, срок действия.
- Переписывает историю трафика со старого email на новый.

**Вывод команды:**

```
✅ <panel>: обновлено 2, переименовано 1, потеряно 0

Итого: обновлено 2, переименовано 1, не найдено в панели 0
```

**Что значит «потеряно N»:**

Связки, которые есть в БД, но по UUID не найдены в панели. Возможные причины:

- Клиент удалён из панели вручную.
- UUID в БД не совпадает с UUID в панели (редко, при ручном редактировании).
- Панель недоступна.

При «потеряно» бот пишет в лог:

```
[sync] <panel>: потеряна связка tg_id=..., email=..., uuid=...
```

**Что делать:** проверь руками в панели, есть ли этот клиент. Если нет — сделай `/revoke`.

### 6.9. Особенность для админов с подпиской

Если админ создаёт подписку **самому себе** (через `/addclient <свой_tg_id> ...`), reply-клавиатура **не заменяется** на клиентскую. Остаётся админская.

Чтобы получить свою sub-ссылку — используй `/mylink`.


## 7. Сценарии работы

### 7.1. Выдача подписки новому клиенту

1. **Клиент** нажимает `/start` и **«📝 Отправить заявку»**.
2. **Админ** получает уведомление с TG ID, именем и username клиента.
3. **Админ** создаёт клиента:

   ```
   /addclient <tg_id> <email> <panel> <id1> [id2]
   ```

4. **Бот** спрашивает HWID лимит (0–10, где 0 — безлимит).
5. **Бот** спрашивает срок подписки — кнопками или датой `ГГГГ-ММ-ДД`.
6. **Бот** спрашивает комментарий (виден только админам).
7. **Бот** показывает превью и запрашивает подтверждение.
8. **Бот** создаёт клиента, отправляет клиенту sub-ссылку и reply-клавиатуру, админу — отчёт с `Sub ID`.

### 7.2. Повторная выдача ссылки

Клиент нажимает **🔗 Ссылка подписки** или пишет `/mylink`.

- Если подписка на паузе — бот ответит «приостановлена».
- Админ может получить ссылку через `/getlink <tg_id> [email]` (см. раздел 7.8).

### 7.3. Пауза и возобновление

```
/pausesub <tg_id> <email> → [✅ Да]
```

Клиент вернулся:

```
/resumesub <tg_id> <email> → [✅ Да]
```

Бот продлит срок на число дней паузы. Для бессрочных подписок срок не меняется.

### 7.4. Продление

```
/extendsub <tg_id> +30                # +30 дней
/extendsub <tg_id> 2027-01-01         # до даты
/extendsub <tg_id> +30 <email>        # конкретная связка
```

### 7.5. Удаление

```
/revoke <tg_id> <email> → [✅ Да]
```

Удаляет клиента из панели **и** из БД бота.

### 7.6. Переименование клиента после промо

Клиент зашёл в промо-период под email `prm_ivan`, потом оплатил. Меняем email:

```
/rename <tg_id> prm_ivan ivan_paid
```

**Что происходит:**
- Панель обновляет email клиента.
- БД обновляет связку.
- История трафика перепривязывается к новому email.
- Клиент **ничего не замечает** — sub-ссылка и настройки остаются прежними.

### 7.7. Синхронизация после правок в панели

Если админ менял что-то **руками** в панели (например, продлил подписку):

```
/sync
```

Бот обойдёт панели, найдёт связки по UUID и обновит БД. Обычно занимает несколько секунд.

### 7.8. Выдача ссылок клиенту (`/getlink`)

С версии v1.2 команда `/getlink` работает в два шага. Админ вводит:

```
/getlink <tg_id>
```

Бот отвечает сообщением с выбором:

```
🔗 Что выдать для клиента <tg_id>?
Найдено подписок: 1

[ 📦 Ссылка на подписку ]
[ 🧩 Ссылки на все конфигурации ]
[ ❌ Отмена ]
```

**📦 Ссылка на подписку** — то, что было и раньше: бот выдаёт одну строку вида:

```
https://<PANEL_IP>:<SUB_PORT>/<SUB_PATH>/<sub_id>
```

Клиент импортирует её в приложение, оно само подтягивает список серверов и обновляет их при каждом запуске.

**🧩 Ссылки на все конфигурации** — бот идёт в API панели (`/panel/api/clients/links/:email`), получает массив готовых ссылок (по одной на инбаунд) и присылает **отдельным сообщением на каждую связку**:

```
🧩 Конфигурации клиента <tg_id>
Панель: <panel>
Подписка: <email> — ▶️ активна

Найдено конфигов: 6

1. <inbound_name>-<email>
<code>vless://<uuid>@<panel-host>:443?...</code>

2. <inbound_name>-<email>
<code>vless://<uuid>@<panel-host>:14839?...</code>
...
```

Каждая ссылка обёрнута в `<code>` — тап копирует целиком, не открывая браузер.

**Когда использовать какой вариант:**

| Ситуация | Что давать |
|----------|------------|
| Клиент в РФ с обычным провайдером | 📦 sub-ссылку |
| Клиент в Туркменистане | 🧩 прямые конфиги (sub-порт блокируется) |
| Клиент на iOS | 🧩 конфиги (XHTTP на iOS не работает) |
| Клиент в приложении, которое не умеет sub | 🧩 конфиги |

**Запасной вариант:** если панель недоступна по API, бот сообщит «Панель не отдала конфигурации, попробуй позже» — повтори запрос.

### 7.9. Рассылка (`/broadcast`)

```
/broadcast Привет всем                     # всем пользователям бота
/broadcast <tg_id> Привет Ивану            # конкретному
```

Перед отправкой бот показывает превью с инициатором и текстом. После подтверждения — рассылает.

В отчёте:

```
✅ Рассылка завершена

Доставлено: 42 из 45
- Успешно: 42
- Не доставлено: 3

Первые неудачные ID: <tg_id_1>, <tg_id_2>, ...
```

**Особенности:**

- **Админы тоже получают** рассылку — для фактчека.
- Если HTML в тексте сломается — бот автоматически пробует отправить как plain text.
- Между сообщениями пауза 50 мс (не более 20 msg/sec, чтобы не поймать flood-лимит).


## 8. Автоматические задачи

| Задача | Когда | Что делает |
|--------|-------|-----------|
| `check_inbounds_job` | Каждые 6 часов | Проверяет связь с панелями, алерт при недоступности и истекающих инбаундах |
| `record_traffic_job` | Ежедневно в 23:50 | Снимок трафика всех клиентов |
| `daily_report_job` | Ежедневно в 8:00 (если включён) | Дневной отчёт админам |
| `client_expiry_notification_job` | Ежедневно в 9:00 | Напоминания клиентам за 7 и 3 дня |
| `client_expired_notification_job` | Ежедневно в 23:59 | Уведомление клиенту в последний день подписки |
| `admin_expired_notification_job` | Ежедневно в 6:00 | Алерт админам на следующий день после истечения |
| `auto_sync_job` | Ежедневно в 00:01 | Автосинхронизация БД с панелями, отчёт админам при изменениях |

Время — в часовом поясе из `config.yml`.

**Отчёт заработает через сутки** — нужно два снимка трафика.

**Напоминания клиентам не срабатывают для подписок на паузе** — клиента не тревожим, пока он сам не вернётся.

## 9. Суперадмин

**Первый ID в `users.admin_users`.**

Если его нет — **все админские команды заблокированы**, бот напишет: «Суперадмин не назначен. Зайди на сервер и добавь ID первым в `users.admin_users` файла `config.yml`».

Чтобы назначить/сменить — правь `config.yml` руками и перезапускай бота.

## 10. Журнал действий (`audit.log`)

Все действия админов и суперадминов пишутся в **`data/audit.log`**.

### 10.1. Что и когда пишется

- **Каждая админ-команда** — при вызове (декоратор `@audit_command`).
- **Результат операций** — после выполнения (`_do_*`, `pending_input_handler`, ручные команды).

Пример:

```
2026-01-15 10:00:00 [<admin_tg_id> @<admin_username>] /broadcast args=['<tg_id>', 'Test', 'message']
2026-01-15 10:00:01 [<admin_tg_id> @<admin_username>] broadcast OK recipients=1 delivered=1 failed=0
```

### 10.2. Формат

```
<YYYY-MM-DD HH:MM:SS> [<admin_tg_id> @<admin_username>] action [args=[...] | details]
```

Действия начинаются с `/` (вызов команды) или без (результат операции).

### 10.3. Статусы

| Статус | Значение |
|--------|----------|
| **`OK`** | Полный успех |
| **`PARTIAL`** | Частичный: часть связок обработана, часть — нет. Или: в панели ок, в БД ошибка |
| **`FAIL`** | Ни одна связка не обработана. Обычно с `reason="..."` |

### 10.4. Разделитель дней

Перед первой записью нового дня бот вставляет визуальный блок:

```
╔══════════════════════════════════════════════════════════════════════════╗
║  📅  <YYYY-MM-DD>                                                        ║
╚══════════════════════════════════════════════════════════════════════════╝
```

### 10.5. Ротация

При превышении **1 МБ** файл переименовывается в `audit.log.1` (старый `.1` удаляется), начинается новый. Логика встроена в `audit.py` — cron не нужен.

### 10.6. Полезные команды

```bash
# Последние 30 записей
tail -30 <PROJECT_DIR>/XUIHelper/data/audit.log

# Только операции broadcast
grep ' broadcast ' <PROJECT_DIR>/XUIHelper/data/audit.log

# Все ошибки
grep 'FAIL' <PROJECT_DIR>/XUIHelper/data/audit.log

# Что делал конкретный админ
grep '@<admin_username>' <PROJECT_DIR>/XUIHelper/data/audit.log

# Все успешные создания клиентов
grep 'addclient OK' <PROJECT_DIR>/XUIHelper/data/audit.log

# Всё за конкретный день
grep '^<YYYY-MM-DD>' <PROJECT_DIR>/XUIHelper/data/audit.log
```

### 10.7. Что НЕ логируется

- Действия клиентов (слишком много, не задача аудита).
- Внутренние шаги диалогов (`/addclient` пишет одну строку, а не пять).
- Факты запуска/остановки бота.

## 11. Развёртывание

### 11.1. Выбор сервера

Возможны три схемы:

| Схема | Когда подходит |
|-------|----------------|
| Бот и панель на одном сервере | Панель и бот делят 1 ГБ+ RAM, IP сервера не блокируется |
| Бот на отдельном сервере, панель за границей | Бот в РФ, панель за рубежом, SSH-туннель для Telegram |
| Бот и панель за границей | Telegram доступен напрямую, нет туннеля |

Эта инструкция описывает **вторую схему** — бот в РФ, панель за границей, SSH-туннель для Telegram.

### 11.6. SSH SOCKS5-туннель

**Проверь, доступен ли Telegram напрямую:**

```bash
curl -s --max-time 10 https://api.telegram.org/bot123:test/getMe
```

**Если ответ `{"ok":false,...}` — Telegram доступен, туннель не нужен.** Пропусти этот раздел.

**Если timeout** — туннель обязателен.

```bash
# Ключ
ssh-keygen -t ed25519 -C "tunnel@xuihelper" -f ~/.ssh/id_ed25519 -N ""

# Копирование ключа на зарубежный сервер
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<REMOTE_SERVER>

# Проверка
ssh -o PasswordAuthentication=no root@<REMOTE_SERVER> "echo OK"
```

Создай `/etc/init.d/tg-tunnel`:

```bash
cat > /etc/init.d/tg-tunnel << 'EOF'
#!/sbin/openrc-run

name="Telegram SSH tunnel"

command="/usr/bin/ssh"
command_args="-N -D 127.0.0.1:1080 \
    -o ServerAliveInterval=30 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -o StrictHostKeyChecking=accept-new \
    -o BatchMode=yes \
    root@<REMOTE_SERVER>"

command_user="root"
pidfile="/run/${RC_SVCNAME}.pid"

command_background="yes"
output_log="/var/log/tg-tunnel.log"
error_log="/var/log/tg-tunnel.err"

respawn_delay=5
respawn_max=0

depend() {
    need net
}
EOF

chmod +x /etc/init.d/tg-tunnel
rc-update add tg-tunnel default
rc-service tg-tunnel start
```

**Проверка:**

```bash
ss -tlnp | grep 1080
curl -s --max-time 10 --proxy socks5h://127.0.0.1:1080 https://api.telegram.org/bot123:test/getMe
```

**Важно:** используй `socks5h://` (а не `socks5://`) — тогда DNS-резолв произойдёт на удалённом сервере. Иначе curl будет резолвить у себя, найдёт IPv6 адрес Telegram, а у удалённого сервера может не быть IPv6-маршрута.

### 11.7. OpenRC-сервис для бота

```bash
cat > /etc/init.d/xuihelper << 'EOF'
#!/sbin/openrc-run

name="XUIHelper Telegram bot"

command="<PROJECT_DIR>/XUIHelper/.venv/bin/python"
command_args="-u main.py"
command_user="root:root"
directory="<PROJECT_DIR>/XUIHelper"
pidfile="/run/${RC_SVCNAME}.pid"

command_background="yes"
output_log="/var/log/xuihelper.log"
error_log="/var/log/xuihelper.err"

export HTTPS_PROXY="socks5://127.0.0.1:1080"
export HTTP_PROXY="socks5://127.0.0.1:1080"
export ALL_PROXY="socks5://127.0.0.1:1080"
export NO_PROXY="127.0.0.1,localhost"

respawn_delay=10
respawn_max=0

depend() {
    need net
    use tg-tunnel
}
EOF

chmod +x /etc/init.d/xuihelper
rc-update add xuihelper default
rc-service xuihelper start
```

**`NO_PROXY` — обязательно.** Без него `httpx` погонит через SOCKS5 и запросы к панели. Если панель имеет внешний IP — добавь его в список через запятую (`NO_PROXY="127.0.0.1,localhost,<PANEL_IP>"`).

**Проверка:**

```bash
rc-service xuihelper status
tail -20 /var/log/xuihelper.err
```

### 11.8. Logrotate

```bash
cat > /etc/logrotate.d/xuihelper << 'EOF'
/var/log/xuihelper.log /var/log/xuihelper.err /var/log/tg-tunnel.log /var/log/tg-tunnel.err {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF

echo "0 3 * * * logrotate /etc/logrotate.d/xuihelper" >> /etc/crontabs/root
rc-service crond restart
```

**`data/audit.log` в logrotate не нужен** — он ротируется самим ботом.

## 13. Особенности Туркменистана

Специфичный регион с агрессивной фильтрацией трафика. Ниже — что выяснено на практике.

### 13.1. Блокировка sub-порта

**Симптом:** клиент не может забрать подписку по ссылке, хотя панель доступна, а VPN-конфиги работают напрямую.

**Причина:** провайдер блокирует порт sub-сервиса (обычно 2096), но не блокирует порты Xray-инбаундов (443, 11440 и т.д.).

**Решение:** использовать `/getlink` → **«🧩 Ссылки на все конфигурации»**. Каждая ссылка идёт на порт конкретного инбаунда — их провайдер пропускает.

### 13.2. HWID-гейт в 3x-ui 3.8.5+

**Симптом:** sub-ссылка отдаёт 404, хотя клиент существует и активен.

**Причина:** с версии 3.8.5 панель при `limit_hwid > 0` требует от клиента заголовок `X-HWID` в sub-запросе. Приложения, которые его не отправляют (например, старые версии HAPP), получают 404.

**Решение:**
- Снять `limit_hwid` в панели (ставить 0).
- Или использовать HAPP 4.6+ — он умеет отправлять `X-HWID`.
- Или раздавать конфиги напрямую через `/getlink`.

### 13.3. Hysteria2 и UDP

**Симптом:** инбаунд Hysteria2 в подписке, но HAPP не подключается к нему.

**Причина:** Hysteria2 работает поверх UDP/QUIC. Провайдеры в ТМ часто применяют QoS или блокируют UDP/QUIC.

**Решение:** оставить один рабочий протокол (VLESS+Reality), либо дать клиенту только его конфиг через `/getlink`.

### 13.4. HAPP и несколько инбаундов в подписке

**Симптом:** в подписке 6 инбаундов — не работает ничего. Оставляешь один — работает.

**Причина:** HAPP пытается подключиться ко всем профилям **последовательно**. Если первый несовместим (например, XHTTP+Reality на iOS), клиент зависает на нём и не переключается.

**Решение:**
- Оставить в подписке только совместимые инбаунды для конкретной платформы.
- Или включить «Автовыбор сервера» в настройках HAPP.
- Или дать клиенту один рабочий конфиг через `/getlink`.

### 13.5. Блокировка порта 80 на исходящие

**Симптом:** не выпускается Let's Encrypt через HTTP-01.

**Причина:** провайдер ТМ блокирует исходящий трафик на порт 80.

**Решение:** использовать **Let's Encrypt for IP** — он валидируется через TLS-ALPN-01 (порт 443), порт 80 не нужен.

## 14. FAQ

**В: Клиент не получает подписку.**
О: Проверь, что он нажал `/start`. Без этого Telegram не даёт ботам писать первыми.

**В: Как узнать ID инбаунда?**
О: `/inbounds <panel>` покажет список с ID, именами, протоколами и портами.

**В: Клиент просит вернуть ссылку.**
О: `/getlink <tg_id> <email>` — выбери способ (sub или конфиги). Ссылки придут в личку админу.

**В: Почему `/report` показывает «данные недоступны»?**
О: Отчёту нужны два снимка трафика (за вчера и позавчера). Первые сутки — не работает.

**В: Забыл, на каком инбаунде сидит клиент.**
О: `/listclients` — увидишь список с инбаундами и комментариями.

**В: Что делать, если панель отключена (`disabled: true`)?**
О: Включи её в `config.yml` или через `/setting` (суперадмин). Пока отключена — все операции с ней блокируются.

**В: Как понять, кто из админов что делал?**
О: `cat data/audit.log` или `grep '@<admin_username>' data/audit.log`. Формат — человекочитаемый, по строке на событие.

**В: Как сменить имя клиента после промо-периода (`prm_*` → обычное)?**
О: `/rename <tg_id> prm_ivan ivan_paid`. Sub-ссылка не меняется, клиент ничего не замечает.

**В: Бот перестал отвечать после смены сертификата панели.**
О: Проверь `tail -50 /var/log/xuihelper.err`. Если видишь `httpx.ConnectError` или `SSLCertVerificationError` — панель сменила сертификат, бот не может подключиться. Перезапусти: `rc-service xuihelper restart`.

**В: Sub-ссылка не открывается у клиента в ТМ.**
О: См. раздел 13. Кратко — используй `/getlink` → «🧩 Ссылки на все конфигурации».
